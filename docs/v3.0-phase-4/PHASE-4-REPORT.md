## 3 · How the mapping is implemented

`MGS.assets.attach` (25 members, on the object Phase 3 already froze) — full contract in
`04-ATTACHMENT-MAPPING-REFERENCE.md`. The pieces that matter for review:

* **Order comes from one array.** `map()` sorts `MGS.assets.meta()` by the `n` Phase 3 assigns at
  `add()` time, so the tile list, the strip, the map, the usage lines, the attach list and any future
  adapter all read the same numbering. Reordering renumbers; nothing is derived from a file name.
* **Every sentence is table-driven.** 15 role sentences (the brief's four verbatim, Phase 3's eleven kept,
  three with an added `ROLE_KEEP` clause so nothing is lost), 11 treatment sentences over 12 catalogue
  entries ("no preference" produces none), 11 position sentences over 12. The suite enumerates
  `assets.roles()/treatments()/positions()` and fails if any id is unmapped — that is the guarantee behind
  "never apply a role's instruction to another role" (`P4 045`, `P4 093`, `P4 155…176`).
* **Numbering is a token, not prose.** Templates are written `Image N` and only `n2()` substitutes the
  real number, so a sentence can never be emitted anonymously; `check()` fails the run if the literal
  `Image N` ever survives into a prompt.
* **`check()` reports instead of throwing**: dense numbering, no duplicates, no cross-references between
  images (user notes are excluded because they are quoted), every usage line numbered, no first-person
  phrasing, one map section, balanced fences, <30 KB, no `{}`, no image bytes.
* **`spec(platform)`** assembles the brief's 16 sections in order from v2.0's own `gPr` lines (section
  headers matched and reused verbatim), plus the map, the usage instructions, a hierarchy derived from the
  content the user actually filled, `not set` where nothing exists, v2.0's negative text, and the attach
  list. Building it writes nothing into `gPr` and never re-runs `GEN()` (`P4 113`).
* **The four copy outputs** live in a row that is a sibling of `#oTabs`/`#oBody`, so v2.0's `rOut()`
  rebuild cannot delete it and nothing copied contains a button. Each uses the clipboard API with an
  `execCommand` fallback and a refusal when both are missing (`P4 148` proves all three paths).
* **Preparation for the Rules Engine, honestly labelled**: `state.assets.exactText` + `MGS.rules.exactText()`
  return `{rule:{id:'exact_text_only', source:'asset', field:'content.text', prepared:true}}`; the Rules
  Engine has not run and no prompt line claims otherwise.
* **Storage**: one key, `mgs.attach.v1`, 3 fields holding one boolean, both writes guarded (`P4 232` proves
  the app survives a throwing `setItem` on `file://`); `MGS.assets.state().items` still holds metadata only
  (`dataUrl` is only ever `''`), and Phase 3's storage surface is untouched.

## 9 · Known limitations (all deliberate, all tested for)

1. **`TEXT RULES` is preparation, not enforcement.** `MGS.rules.exactText()` reports the rule with
   `prepared:true`; nothing rejects a prompt that changes the user's words. Wiring it into the Rules Engine
   is Phase 5/6 work.
2. **Variant cards and the negative prompt are still not augmented** with the mapping (unchanged from
   Phase 3). The specification *shows* the negative text, and the prompt block *mentions* it in
   `PRODUCTION REQUIREMENTS`-adjacent wording, but v2.0's own `gNeg()` output is untouched.
3. **One sentence, two orientations.** Inside the prompt the attach list says "in the same order shown
   **above**" (the list is inside the prompt it refers to); the standalone payload and the card keep the
   brief's "**below**" wording, because there the list really is above the paste step. `P4 051` pins the
   short half; the difference is a consequence of the block being self-contained.
4. **`#icount` is still v2.0's problem**: `icount === 'multiple'` continues to drop v2.0's own `IMAGES:`
   line (DFR 001), because mirroring a broken branch would change v2.0's prompt shape. The mapping is
   complete for all N images regardless, so no information is lost — but the v2.0 line stays missing.
5. **The specification is a view of the active platform at copy time**, not a live validator: it reports
   `not set` / `none selected` honestly instead of filling gaps, and if the user changes the form after
   generating, they must press `Re-map prompt` (or Copy again after regenerating) — same staleness rule
   Phase 3 accepted for its own block.
6. **No real browser and no clipboard in this environment**: layout claims are structural, and the copy
   paths are verified through the API contract (payload identity + fallback + refusal), not a user-visible
   clipboard. `execCommand` and `navigator.clipboard` are both implemented and both exercised.
7. **Storage is preference-only.** `mgs.attach.v1` keeps one boolean; there is no attachment manifest on
   disk, because file names and byte payloads belong to Phase 3's two keys and are not duplicated here.
8. **v2.0's own defects stay deferred** (DFR 001–009), including the `#negB`-inside-copy-target bug — my
   copy row is placed outside every copied region so the class of bug cannot recur in new code, but v2.0's
   own button still lives inside its box.
